### Back contract check (requested items 1, 2, 4)
- **Schedule open**: `canPop: false`, then `onPopInvokedWithResult(didPop:false)`, then `_closeDvr`. Focus returns to ⏸ through `_requestFocusWhenReparented`. The second Back pops. Correct.
- **Anything else**: `canPop: true`. The route pops once. Correct.
- **Key-up / KeyRepeat**: `playPauseFocus` returns `ignored` for `goBack` before any other check, for down, repeat and up (:106-108). `arrowBackFocus` ignores every non-KeyDown event and ignores goBack explicitly (:166-170). `_scheduleFocus` and the program cards have no key handler. `_inkFocus` has none. The rest of the focus chain up to the app root has no goBack handler: `AppScaffold`'s goBack handler (app_scaffold.dart:87) is only on page routes, not above the root Navigator, and `StbPowerGuard` only observes and returns `false`. Both key-down and key-up therefore reach Android unhandled, so Activity `onKeyUp` gives exactly one `onBackPressed`. No double-fire.
- **No handler pops while the framework also pops**: the only imperative pops are the ← button `onPressed` and `arrowBackFocus`'s Enter/Select. Neither fires on goBack. Select is handled on KeyDown by the node before the app-level `Shortcuts(select → ActivateIntent)`, so it pops once.
- **Visibility listener vs Up (item 4)**: in the `wasVisible` branch, `handleVisibility()` emits an equal state. Cubit deduplicates it, so the listener does not fire and nothing races `arrowBackFocus.requestFocus()`. In the hidden branch, the listener only re-requests ⏸, which already has focus. When auto-hide fires with ← focused, focus returns to ⏸, so OK on a blank screen toggles play/pause and does not exit. I found no state where an invisible ← keeps focus.
- **Loading / re-initialising the controller**: `VodFullScreen` and its PopScope are not mounted (app_video_player.dart:133-138), so Back pops the route. Same as before, and never trapped.

### Phones (item 3)
`AppVideoPlayer` is used only by `VideoPlayerPage` (video_player_page.dart:130). Removing `PopScope(canPop:false)` turns the system back gesture/button back on in the phone player. Before, the on-screen ← was the only exit. The gesture goes through the same `Navigator.pop`, so `VideoPlayerPage.dispose` resets orientation exactly as the ← path always did. No new regression. Predictive back works because `canPop` only turns false while the schedule is open, and the schedule opens only via D-pad Down.

## Notes
- **Do the tests exercise the real pop path (item 5)?** Yes, for the framework half. `handlePopRoute` goes through `Navigator.maybePop` and the route's PopScope, so putting back a `PopScope(canPop:false)` anywhere on the route fails 4 tests. Marking `goBack` `handled` on ⏸, on ← or on any ancestor in the controls fails the key test. Gaps: the schedule-open focus positions, focus-location assertions and auto-hide focus (C3), and the embedding re-dispatch, which needs a device (C1). Using `platform: 'web'` for the goBack simulation is a test-harness workaround. Handlers only compare `logicalKey`, so it is valid.
- **Root-cause wording**: plan step 2 and the report say `arrowBackFocus` "swallows Back (`skipRemainingHandlers`)". That is not accurate. `KeyEventResult.skipRemainingHandlers` stops the framework's bubbling but reports the event as not handled to the embedding, so Android still re-dispatches it as a pop. The real traps were the `PopScope(canPop:false)` and `_inkFocus` returning `handled`. This does not change the fix (the explicit goBack ignore at :168 is harmless), but the learnings candidate should say "`handled` traps; `skipRemainingHandlers` does not".
- **pubspec.lock staging**: besides the `meta` and `test_api` churn, the working-tree lock also lowers the `sdks: dart:` lower bound (`>=3.10.0-0` to `>=3.9.0-0`). When staging only the `video_player_platform_interface` marker line, leave that line out too.
- **KB contradiction raised by the dev**: I agree with it from reading the code. The old `_inkFocus` goBack handler could only toggle the controls if the Back key reached Flutter as a key event first. The entry's conclusion (one PopScope authority, no raw Back handler) still holds. Its mechanism sentence needs "key first, route pop only if unhandled".
